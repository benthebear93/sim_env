# Experimental Setup 1: UR5e and WSG-50 on a Siegmund Welding Table

This repository contains the MuJoCo representation of the current physical
**Experimental Setup 1**: a UR5e mounted on a Siegmund welding table, with a flange
adapter and a Schunk WSG-50 parallel gripper.

The scene uses the table coordinate system from
`post_grasp_tactile_manipulation` and the UR5e URDF from `post_grasp_repair`.
The assembly follows this frame hierarchy:

```text
Table → UR controller base → URDF model → tool0 → flange adapter / WSG-50
```

The original assets, calibration, and installation corrections are preserved
locally. Loading or rebuilding the scene does not require the original
repositories or a connection to the physical robot. The approximations listed
below distinguish this simulation model from a complete hardware digital twin.

## Running the scene

The scene has been validated with Python 3.10 and MuJoCo 3.1.5.

```bash
cd /home/haegu/sim_env
python3 scripts/view_scene.py
python3 scripts/view_scene.py --step
```

The default viewer holds the initial configuration. `--step` enables dynamics,
including gravity and position servos. Actuator controls can then be adjusted
through the MuJoCo UI.

For a new environment, copy the repository and install its dependencies in
editable mode. Keep the entire repository: mesh assets live in `assets/`,
outside the Python package directory.

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[test]'
.venv/bin/python scripts/view_scene.py
```

After editing the configuration, regenerate and validate the scene:

```bash
python3 scripts/build_scene.py
python3 -m pytest -q
python3 scripts/view_scene.py --render outputs/bench_overview.png --software
python3 scripts/view_scene.py --render outputs/tool_closeup.png --view tool --software
```

`--software` selects Mesa software EGL rendering. Interactive viewing requires
a desktop display. The runtime does not import RTDE or WSG network drivers.

Rendered views: [assembly overview](images/exp1.png) and
[flange adapter and gripper](images/exp1_tool.png).
These images can be regenerated with the commands above.

## Table coordinates and through-holes

- Tabletop: `z = 0 m`; the plate occupies `z = -0.035 … 0 m`.
- XY extent: `x = 0 … 1.2 m`, `y = -0.8 … 0 m`.
- Hole radius: `0.008 m`; center spacing: `0.050 m`; edge offset: `0.025 m`.
- Grid: 24 × 16 = **384 through-holes**. The radius and spacing are adopted
  from the existing viewer for this setup. Threads are omitted.
- Grid indices are one-based. The x-index increases along +x; the y-index
  increases along −y. Hole `(13, 9)` is centered at `[0.625, -0.425, 0] m`.
- Hole centers are available as named sites, such as `table_hole_13_09`.

Each hole is open in both visual and collision geometry. The material around
each hole is represented by 32 convex prisms. The circular opening is
approximated by a 32-sided polygon, giving a maximum radial deviation of
approximately 0.039 mm at an 8 mm radius. There is no solid collision box
covering the holes.

This decomposition follows MuJoCo's
[convex collision geometry requirements](https://mujoco.readthedocs.io/en/3.1.5/computation/index.html#collision-detection).
The table is fixed; table legs and a floor are not modeled.

## Installation pose and coordinate frames

The original calibration places the UR controller base at
`[0.124614895, -0.375523056, 0.023194976] m` in the calibration world frame.
Following the tactile runtime, this scene preserves the calibrated XY position
and rotation while setting the base height above the tabletop to **0.041 m**.
The original 3×3 rotation matrix is used, including its small roll and pitch.

The default is `world_origin_in_calibration_xy_mm = [0, 0]`.
To use the origin convention of the repair repository's Allen-key viewer,
change this value to `[0, 50]`.

```text
T_table_model = T_table_ur_base × T_ur_base_model
```

`T_table_model` maps URDF model coordinates into the table frame.
`T_table_ur_base` is the pose of the UR controller base in the table frame.
`T_ur_base_model` maps nominal URDF model coordinates into controller base
coordinates. It combines a 180° rotation about z with a translation fitted to
the existing measured insertion reference. The default fitted translation is
approximately `[-7.7952, 0.0654, 6.2553] mm`. Consequently, the nominal URDF
base mesh origin differs from the `ur_base` frame origin.

The scene's `flange` site coincides with **URDF `tool0`, the UR controller's
zero-TCP frame**. The URDF link named `flange` has a different orientation and
must not be substituted for `tool0`. The adapter and WSG-50 extend along
`tool0` +z, following the existing preview. The `tcp` site is located at
`[0, 0, 0.145] m` relative to `tool0`.

The model reproduces nominal URDF kinematics and the existing translation
correction from one measured posture. It does not identify robot-specific
factory kinematic parameters or establish accuracy across the full workspace.
The original calibration RMSE of approximately 0.2415 mm describes the seven
base calibration samples, not the positioning accuracy of the entire assembly.

## Geometry fidelity and modeling assumptions

| Component | Representation |
|---|---|
| UR5e | Original URDF joint transforms, axes, limits, inertias, and visual meshes |
| UR5e collision | MuJoCo convex hulls of the original link STL meshes; detailed concavities are not retained |
| Base spacer | Visual cylinder of radius 75 mm spanning the table-to-model-base gap; collision disabled |
| Flange adapter | Cylinder of radius 32 mm and thickness 20 mm from the existing preview; detailed CAD and bolt holes are not included |
| WSG body | Existing glTF mesh, SDF body dimensions, and mass of 0.988882 kg |
| Fingers | 12 × 20 × 70 mm boxes matching the existing preview dimensions; assumed mass of 0.05 kg per finger |
| Tactile hardware | Actual asymmetric fingers, GelSight housings, and gel compliance are not included |
| Contact and control | Friction, damping, and position servo gains are simulation defaults, not identified hardware parameters |

The original stock finger meshes are also stored as OBJ files, but the current
assembly uses the simplified box fingers from the tactile preview. These can
be replaced when the physical finger CAD is available.

WSG body inertia is calculated from its box dimensions and mass. The large
inertia constants in the source SDF are not used directly. The flange adapter
assumes aluminum density.

Both finger joints use the convention:

```text
q = inner jaw gap / 2
```

`q` is each finger's outward displacement in meters. The commanded inner jaw
gap ranges from 0 to 110 mm, with an initial opening of 50 mm. Both actuators
receive the same target to command symmetric opening. This simulation position
target is distinct from the nominal part width used by the physical WSG GRIP
command.

## Python API

```python
import mujoco
from sim_env.bench import load_scene, grid_hole_position, set_gripper_opening

model, data = load_scene()  # Initializes the ready keyframe.
target = grid_hole_position(13, 9)
tcp_world = data.site("tcp").xpos.copy()
set_gripper_opening(model, data, 0.030)
for _ in range(500):
    mujoco.mj_step(model, data)
```

When loading directly with `MjModel.from_xml_path`, explicitly apply the
`ready` keyframe using `mj_resetDataKeyframe`. The model has six UR joints,
two WSG sliding joints, and eight actuators.

Visualization group 2 contains visual meshes; group 3 contains collision
meshes that can be hidden; site group 4 contains frame and hole sites.
The adapter and finger boxes share their visual and collision geometry.

## Validation

The current setup passed **12 tests** in `tests/test_bench.py`, covering:

- Agreement with source URDF forward kinematics at three joint configurations.
- Reproduction of the measured insertion reference and the TCP offset.
- Ray passage through all 384 holes.
- Sphere passage through a hole and actual contact with the tabletop and hole wall.
- Jaw opening dimensions and stable dynamics during gripper opening and closing.
- Scene loading after relocation to a different directory.
- Integrity of the copied source assets through SHA-256 checks.

Validation runs entirely offline and does not connect to the physical robot.
